# Arduino 单线莫尔斯电报机项目 PRD

## 1. 项目名称

Arduino Wired Telegraph  
基于两台 Arduino Uno 的单线半双工莫尔斯电报通信系统

---

## 2. 项目背景

本项目目标是使用两台 Arduino Uno，构建一套“电报机式”的有线通信系统。  
系统通过单根数据线进行双向通信，使用莫尔斯编码承载字符信息，并设计一套适用于单线半双工场景的轻量级链路仲裁协议。

用户可以在任意一端的串口监视器输入文本，设备会将文本转换为莫尔斯编码并发送给对端。  
对端接收到后进行解码，并在串口中打印还原后的消息。

为了增强“电报机”的交互感，发送端在发送过程中蜂鸣器鸣响，接收端在接收过程中点亮绿色 LED。  
系统还需要具备“线路空闲检测”“冲突避免”“发送等待”“基本帧结构”“校验与确认”等机制，行为上类似一个极简版的单线串口通信协议。

---

## 3. 项目目标

### 3.1 主要目标

1. 使用两台 Arduino Uno 完成双向文本通信。
2. 仅使用一根数据线完成信号传输。
3. 使用莫尔斯编码表示字符内容。
4. 在串口输入任意文本后，自动发送给对端。
5. 对端收到后，自动解码并在串口打印文本。
6. 发送时本机蜂鸣器响。
7. 接收时本机绿色 LED 亮。
8. 通过协议设计实现半双工仲裁，避免双方同时发送导致混乱。

### 3.2 次要目标

1. 支持基础错误检测。
2. 支持消息确认（ACK）。
3. 支持超时重发。
4. 保持协议结构清晰，便于后续扩展。
5. 代码易于调试与演示。

## 5. 使用场景

### 5.1 场景一：普通消息发送

1. A 端串口输入 `HELLO`
2. A 检测总线空闲
3. A 按协议申请发送并发送消息
4. A 发送过程中蜂鸣器响
5. B 检测到接收帧，绿色 LED 亮
6. B 解码得到 `HELLO`
7. B 串口打印消息
8. B 返回 ACK
9. A 收到 ACK，发送完成

### 5.2 场景二：双方同时想发送

1. A 和 B 都有待发送消息
2. 两端都先检测线路空闲
3. 若发生几乎同时起发，则通过仲裁机制退避
4. 一端先获得发送机会
5. 另一端等待本次发送结束并在空闲窗口后再尝试

### 5.3 场景三：发送失败重试

1. A 发送消息
2. B 未正确收到或 ACK 丢失
3. A 等待 ACK 超时
4. A 触发重发
5. 达到最大重试次数后上报失败

## 6. 硬件需求

### 6.1 核心器件

- Arduino Uno x 2
- 蜂鸣器 x 2
- NPN 三极管 9013 x 2
- 二极管 x 2
- 绿色 LED x 2
- 限流电阻 x 2
- 若干杜邦线

### 6.2 引脚分配

每台 Arduino：

- `D13`：发送提示蜂鸣器控制输出
- `D12`：接收提示绿色 LED 输出
- `D2`：单线通信数据口（建议）
- `GND`：两台设备共地

### 6.3 接线要求

#### 6.3.1 必须共地

虽然数据传输只使用“一根数据线”，但两台 Arduino **必须共地**，否则电平参考不一致，通信不可靠。  
因此物理连接至少包括：

- 1 根数据线
- 1 根 GND 共地线

#### 6.3.2 总线驱动建议

由于是单线双向通信，不建议双方都直接强推高低电平。  
推荐采用以下策略之一：

1. **开漏/准开漏模拟方式**
   - 空闲时引脚设为 `INPUT_PULLUP`
   - 发送低电平时切换为 `OUTPUT LOW`
   - 发送高电平时释放总线，回到 `INPUT_PULLUP`

2. **外部上拉电阻 + 开漏输出**
   - 更稳定，推荐工程实现

此设计可以降低总线冲突风险，避免双方一高一低强驱动导致硬件风险。

## 7. 功能需求

### 7.1 串口输入发送

1. 用户在串口监视器输入任意文本。
2. 按回车后形成一条待发送消息。
3. 设备将该消息编码后发送给对端。
4. 若总线忙，则进入等待队列或挂起状态。
5. 待总线空闲后再尝试发送。

### 7.2 消息接收与显示

1. 设备持续监听总线。
2. 检测到有效帧后进入接收状态。
3. 将莫尔斯编码还原为字符。
4. 在串口打印收到的原文消息。

### 7.3 发送提示

1. 本机正在发送“莫尔斯符号脉冲”时，蜂鸣器发声。
2. 本机非发送状态时，蜂鸣器关闭。
3. 接收时本机蜂鸣器不得响。

### 7.4 接收提示

1. 本机接收到有效消息期间，绿色 LED 点亮。
2. 接收完成后熄灭。
3. 非接收状态下 LED 保持熄灭。

### 7.5 半双工约束

1. 任一时刻只允许一端占用总线发送。
2. 另一端在对方发送期间必须保持监听，不得抢占。
3. 只有在线路连续空闲达到规定时间后，才能发起新传输。

### 7.6 ACK 确认

1. 接收端正确接收并校验通过后，返回 ACK。
2. 发送端收到 ACK 后，判定本条消息发送成功。
3. 若超时未收到 ACK，则进入重发流程。

### 7.7 超时重发

1. 每条消息允许最多 `N` 次重发。
2. 超过最大次数仍失败，则串口提示发送失败。

## 10. 莫尔斯编码设计

### 10.1 编码范围

首版建议支持：

- `A-Z`
- `0-9`
- 空格
- 少量标点（可选）

串口输入建议先统一转大写。

### 10.2 基本单位时间

定义一个时间基准 `T`：

- 点 `.`：持续 `1T`
- 划 `-`：持续 `3T`
- 同一字符内符号间隔：`1T`
- 字符间隔：`3T`
- 单词间隔：`7T`

建议初版 `T = 100ms` 或 `120ms`，便于观察与调试。

### 10.3 发送表现

- 发送莫尔斯“有信号”时：总线输出有效脉冲，同时蜂鸣器响
- 莫尔斯“间隔”时：总线恢复空闲，蜂鸣器停

## 11. 协议设计目标

协议目标不是直接裸发莫尔斯，而是在“莫尔斯内容”外再包一层简单链路协议，使系统具备：

- 起始识别
- 帧边界识别
- 忙闲判断
- 冲突避免
- ACK 确认
- 重发能力

---

## 12. 链路层协议设计

### 12.1 通信模型

- 双端平等
- 单总线半双工
- 竞争式发送
- 监听优先

### 12.2 总线定义

建议定义：

- 总线空闲：高电平（由上拉保持）
- 总线忙/有效脉冲：低电平

即“拉低总线”表示发送有效信号。

这样更适合单线共享与开漏式实现。

---

## 13. 帧结构设计

每条消息不直接裸发，而是按如下结构发送：

`[PREAMBLE][SOF][HEADER][PAYLOAD][CRC][EOF]`

### 13.1 PREAMBLE（前导同步）

作用：

- 唤醒接收机
- 建立节拍同步
- 表明即将有一帧开始

建议形式：

- `10101010` 风格节拍脉冲
- 或固定 8 个短脉冲

### 13.2 SOF（Start of Frame）

作用：

- 明确帧起始
- 与普通莫尔斯节拍区分

建议使用一个特殊保留序列，例如：

- 长低脉冲 `5T`
- 再空闲 `2T`

作为“帧开始标记”

### 13.3 HEADER（头部）

建议字段：

- `FrameType`：1 字节
- `Seq`：1 字节
- `Length`：1 字节

说明：

- `FrameType`
  - `0x01`：数据帧 DATA
  - `0x02`：确认帧 ACK
  - `0x03`：忙帧 BUSY（可选）
  - `0x04`：错误帧 NACK（可选）
- `Seq`
  - 帧序号，循环使用 0~255
- `Length`
  - 载荷长度（字符数或编码单元数）

### 13.4 PAYLOAD（载荷）

载荷内容为原始文本，发送时实际编码为莫尔斯表示。  
实现上有两种方案：

#### 方案 A：链路层传文本字符，物理层只用普通比特脉冲

- 更像真正串口
- 莫尔斯只作为“提示音逻辑”而不是实际传输内容
- 不符合你“使用莫尔斯编码传输”的原始目标

#### 方案 B：链路层载荷就是莫尔斯编码序列

- 更符合电报机主题
- 接收端需要做莫尔斯解码
- 推荐本项目采用此方案

推荐编码方式：

- `.` -> `1`
- `-` -> `111`
- 符号间隔 -> `0`
- 字符间隔 -> `000`
- 单词间隔 -> `0000000`

即把莫尔斯规范直接映射为时间序列。

### 13.5 CRC（校验）

建议首版使用简单校验：

- `XOR` 校验 1 字节

后续可升级：

- CRC-8

### 13.6 EOF（End of Frame）

帧结束标志。  
建议使用与 SOF 不同的保留时序，例如：

- 连续低脉冲 `2T`
- 空闲 `5T`

或直接用“长时间空闲 > 10T”判定帧结束。

## 14. 仲裁协议设计

### 14.1 设计目标

因为两端都可能在串口输入后发起发送，所以必须定义谁先发。  
要求：

- 简单
- 可在 Arduino Uno 上稳定实现
- 不依赖额外控制线

### 14.2 仲裁原则

采用“监听后发送 + 空闲窗口 + 随机退避”的简化 CSMA/CA 思路。

### 14.3 总线空闲判定

若总线连续保持空闲高电平达到 `IdleThreshold`，则认为线路空闲。  
建议：

- `IdleThreshold = 10T`

### 14.4 发送前监听

任一节点准备发送时，必须先执行：

1. 检查自己是否已有接收进行中
2. 检查总线是否空闲满 `IdleThreshold`
3. 若满足，则进入“抢占等待窗口”

### 14.5 抢占等待窗口

为避免两端完全同时发送，发送前增加一个小退避：

`Backoff = Base + random(0, K)`

建议：

- `Base = 2T`
- `K = 5T`

流程：

1. 检测空闲后不立刻发
2. 先等待一个随机退避时间
3. 退避期间持续监听总线
4. 若发现对方已开始发送，则取消本次发送，转为接收/等待
5. 若退避结束总线仍空闲，则自己开始发送

### 14.6 冲突处理

理论上仍可能出现极小概率同时起发。  
若发送端在发送前导期间检测到总线状态与自己预期不一致，则判定可能冲突，立即停止发送并进入随机退避。

说明：

- 单线共享时，严格的冲突检测能力有限
- 本项目以“冲突预防”为主，而不是复杂的冲突恢复

### 14.7 忙状态处理

若对方正在发送，则本端进入 BUSY WAIT 状态。  
待检测到总线重新空闲并持续达到 `IdleThreshold` 后，再重新参与发送竞争。

## 15. 状态机设计

每个节点建议包含以下状态：

- `IDLE`：空闲监听
- `RX_PREAMBLE`：检测前导
- `RX_FRAME`：接收帧
- `TX_WAIT_IDLE`：等待总线空闲
- `TX_BACKOFF`：随机退避
- `TX_FRAME`：发送帧
- `WAIT_ACK`：等待确认
- `RETRY_WAIT`：重发等待
- `ERROR`：错误恢复

### 15.1 状态切换概要

#### IDLE

- 有串口输入待发送 -> `TX_WAIT_IDLE`
- 检测到前导 -> `RX_PREAMBLE`

#### TX_WAIT_IDLE

- 总线空闲满阈值 -> `TX_BACKOFF`
- 检测到对方发送 -> 保持等待

#### TX_BACKOFF

- 退避期间检测到对方发送 -> `RX_PREAMBLE` 或 `IDLE`
- 退避结束总线仍空闲 -> `TX_FRAME`

#### TX_FRAME

- 发送完成 -> `WAIT_ACK`
- 检测冲突/异常 -> `RETRY_WAIT`

#### WAIT_ACK

- 收到 ACK -> `IDLE`
- 超时 -> `RETRY_WAIT`

#### RETRY_WAIT

- 未超最大次数 -> 回到 `TX_WAIT_IDLE`
- 超过最大次数 -> `ERROR` 后回 `IDLE`

#### RX_FRAME

- 校验成功 -> 打印消息并发送 ACK -> `IDLE`
- 校验失败 -> 丢弃或发 NACK -> `IDLE`

### 16.1 串口波特率

建议：

- `115200`

### 16.2 用户输入规则

1. 一行文本作为一条消息
2. 输入回车后触发发送
3. 空行不发送

### 16.3 串口输出内容

## 17. 指示逻辑需求

### 17.1 蜂鸣器

- 仅本机发送有效莫尔斯脉冲时响
- 发送间隔不响
- 接收时不响
- 等待 ACK 时不响

### 17.2 绿色 LED

- 本机接收到有效帧期间亮
- 帧接收完成后灭
- 仅表示“本机在收”，不是“对方在发但还没识别成功”

---

## 18. 定时参数建议

首版建议值：

- `T = 100ms`
- `IdleThreshold = 10T = 1000ms`
- `ACK Timeout = 20T = 2000ms`
- `Backoff = 2T + random(0..5T)`
- `MaxRetry = 3`

说明：

- 首版以稳定和可观察为优先
- 成熟后可逐步减小 T 提升速度

---

## 19. 错误处理需求

### 19.1 校验失败

- 丢弃本帧
- 不打印错误数据
- 可选发送 NACK

### 19.2 ACK 超时

- 触发重发
- 超过最大次数后报失败

### 19.3 非法字符

若输入包含当前莫尔斯映射表不支持的字符：

- 可直接忽略
- 或替换为 `?`
- 串口打印警告

建议首版策略：

- 仅支持 `A-Z 0-9 空格`
- 其他字符忽略并记录日志

### 19.4 总线卡死

若总线长时间保持忙状态超过阈值：

- 判定异常
- 进入错误恢复
- 重新初始化总线口状态
- 回到监听模式

---

## 20. 验收标准

以下全部满足视为通过：

1. 两台 Arduino Uno 能稳定互发消息。
2. 任一端串口输入文本后，对端串口能正确显示。
3. 发送过程中本机蜂鸣器按发送节奏鸣响。
4. 接收过程中本机绿色 LED 点亮。
5. 对端发送时，本端不会同时乱发。
6. 当双方几乎同时准备发送时，系统能通过退避避免长期冲突。
7. ACK 与超时重发机制有效。
8. 连续发送多条短消息时系统仍能稳定运行。
9. 不出现因总线冲突导致的明显异常死锁。

## 22. 风险与约束

### 22.1 单线通信硬件风险

若直接推挽输出，双方同时驱动可能损坏引脚。  
必须采用安全的单线驱动策略。

### 22.2 时序抖动风险

Arduino 使用 `delay()` 实现虽简单，但可能影响接收准确性。  
后续可考虑基于 `millis()` 或 `micros()` 的非阻塞状态机。

### 22.3 莫尔斯解码复杂度

若直接按脉冲时长实时解析，需保证采样和时间阈值设计合理。  
建议协议层和物理层边界清晰，减少误判。

### 22.4 用户输入速度与缓存

如果用户连续快速输入多条消息，需定义是否支持发送队列。  
首版建议只支持单条待发送缓存，避免复杂度过高。

## 25. 最终定义结论

本项目本质上是一个：

“基于 Arduino Uno 的双节点单线半双工莫尔斯电报通信系统”

其核心设计原则为：

- 单线共享
- 共地通信
- 开漏式安全驱动
- 莫尔斯作为消息承载方式
- 链路层增加起止标志、ACK、重试、仲裁
- 发送响铃、接收亮灯、串口显示文本

该系统既保留“电报机”的表现形式，又具备类似简化串口协议的可靠通信机制，适合作为课程设计、演示项目、电子通信入门实验或 Arduino 协议设计练习项目。
